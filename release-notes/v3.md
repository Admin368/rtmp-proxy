# v3 — Accounts, roles and API keys

Branch `v3` · based on `v2`

The server is no longer open to anyone who knows its address. Publishing requires an API key, the
dashboard requires a login, and streams can be watched and stopped by the people who own them.

## Highlights

**API-key authentication on the RTMP connection.** No key, no publish. The key travels as a query
argument on the stream name, which is the only credential channel RTMP offers and is supported by
every client that lets you type a stream key — OBS, ffmpeg, Streamlabs, hardware encoders.

| Field | Value |
| --- | --- |
| Server | `rtmp://<server>:4001/live` |
| Stream Key | `<stream-name>?key=<your-api-key>` |

The key is stripped from the publish arguments before the outbound URL is built, so it is never
forwarded to YouTube.

**User accounts with roles**, behind a login page.

| | user | admin | creator |
| --- | :-: | :-: | :-: |
| Manage own API keys, within quota | ✅ | ✅ | ✅ |
| See and stop own streams | ✅ | ✅ | ✅ |
| See and stop **all** streams | | ✅ | ✅ |
| Pause / resume **any** API key | | ✅ | ✅ |
| Add and disable accounts | | ✅ (plain users only) | ✅ |
| Restart the server | only if granted | ✅ | ✅ |
| Change roles, quotas, restart permission | | | ✅ |
| Delete accounts | | | ✅ |

There is exactly one `creator`, bootstrapped on first run; it cannot be demoted, disabled or
deleted, so the server can never end up with nobody able to administer it.

**A dashboard that does something.** Live streams — masked name, owner, key, duration, bitrate,
codecs, relay state and source address — refreshing every three seconds, each with a Kill button.
Below it, your API keys with pause / resume / rotate / delete, and for admins the accounts table and
every other account's keys.

**Pause a key, drop the stream.** Pausing is the incident-response action: the stream currently
using that key is dropped immediately and new connections are refused until it is resumed. Admins
can pause anyone's key; only the owner can rotate or delete one.

**Key quotas.** Two per account by default (`DEFAULT_KEY_QUOTA`). The creator can raise or lower it
per account. The creator itself is unlimited.

**Restart button.** Restarts the container without needing the Docker socket mounted: the process
flushes its database, stops every relay, and exits, and Docker's restart policy starts it again.
Admins and the creator have it by role; the creator can grant it to an individual user.

**Per-key destinations.** An API key can carry its own destination URL and stream key, so one server
can feed several YouTube channels — or Twitch, or an internal ingest. Set one and your YouTube key
lives in the database instead of in every encoder's settings.

## Fixed

- **Stream keys are no longer published.** Stream names are masked in the dashboard and in logs
  again, restoring the v1 behaviour v2 dropped — and the dashboard now requires a login regardless.
- **Publishers with no viewers stay visible.** The live-stream list is reconciled against
  node-media-server's real session table every five seconds instead of expiring on a `postPlay`
  timer, so v2's 60-second disappearing act is gone. There is no timeout left to tune.
- **Killing a stream now stops the forward.** Relays are keyed by publisher session, so stopping a
  stream stops its ffmpeg. Previously nothing could stop a relay short of restarting the process.
- **A dropped destination reconnects.** If ffmpeg exits while the publisher is still connected, the
  relay restarts with exponential backoff (1 s doubling to 15 s, ten attempts).
- **`docker build` works.** The Dockerfile copies `yarn.lock`, without which `--frozen-lockfile`
  cannot succeed.
- **Bitrate is reported correctly.** node-media-server's `bitrate` is already in kbps.

## Breaking changes

**Every publisher needs an API key.** Existing OBS profiles will stop working until `?key=<key>` is
appended to the stream key field. This is the point of the release, but plan the cutover.

**Playback from outside the server is refused by default.** This is a forwarder, not a CDN, and
open playback exposed the incoming feed to anyone. Set `ALLOW_REMOTE_PLAYBACK=true` if you were
relying on pulling streams back off port 4001 or 4002. The relay's own ffmpeg reads from loopback
and is unaffected.

**`DATA_DIR` must be a mounted volume.** Accounts, API keys and the cookie-signing secret live in
`$DATA_DIR/db.json`. Without a volume, every restart forgets them and re-bootstraps a fresh creator
account. `docker-compose.yml` mounts one; a hand-rolled `docker run` needs `-v rtmp-data:/app/data`.

**The container needs a restart policy** (`restart: unless-stopped`, already set in
`docker-compose.yml`). Without one, the restart button stops the server rather than restarting it.

**`dist/` is no longer tracked in git.** The image builds from source; there is nothing to commit.

## Upgrading from v2

```bash
git checkout v3
docker compose up -d --build
docker compose logs rtmp-proxy | head -20   # the generated creator password, printed once
```

1. Sign in at `http://<server>:4000` as `creator` and change the password. To choose the first
   password yourself, set `CREATOR_PASSWORD` before the first run.
2. Create an account for each person who streams, and have each of them create an API key.
3. For each key, either set a destination (recommended — the YouTube key then lives on the server),
   or leave it blank to keep the v2 contract where the published stream name *is* the YouTube key.
4. Update each encoder's stream key to `<stream-name>?key=<api-key>`.

Nothing is migrated automatically, because v2 had nothing to migrate: it stored no accounts and no
keys.

## Configuration

New in v3, all optional: `DATA_DIR`, `RTMP_APP`, `DEFAULT_RELAY_EDGE`, `DEFAULT_KEY_QUOTA`,
`CREATOR_USERNAME`, `CREATOR_PASSWORD`, `SESSION_SECRET`, `SESSION_TTL_HOURS`, `SECURE_COOKIES`,
`ALLOW_REMOTE_PLAYBACK`, `FFMPEG_PATH`, `RESTART_EXIT_CODE`. Defaults and meanings are in the
[README](../README.md#configuration).

## Notes

- Passwords are hashed with scrypt; API keys are stored as SHA-256 hashes and shown once at
  creation. A lost key is rotated, not recovered.
- Storage is a single atomically-written JSON file. There is no external database to run, and no new
  runtime dependencies — still just `express` and `node-media-server`.
- Put the dashboard behind HTTPS and set `SECURE_COOKIES=true`. RTMP itself is unencrypted; use
  `rtmps://` destinations where the far end supports it.

## Verified

Publish refused without a key and with a paused key; accepted with a valid one and relayed to a test
RTMP sink; dashboard kill dropping the publisher; an admin pausing another account's key dropping
its live stream and blocking reconnection; per-key destination routing; quota enforcement; admins
blocked from role changes and deletions; disabling an account invalidating its live login; remote
playback refused; the restart button exiting cleanly with no orphaned ffmpeg; accounts surviving a
restart.

**Not verified:** the Docker image build — Docker was not available on the machine where this was
developed.
