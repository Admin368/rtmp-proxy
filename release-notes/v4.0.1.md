# v4.0.1 — Encrypt the outbound leg too

Branch `v4` · follows [v4](v4.md)

v4 encrypted the leg from the encoder to the proxy. This encrypts the other one.

## The outbound leg was plaintext

The relay pushes to `DEFAULT_RELAY_EDGE/<stream key>`, and that URL contains the destination's
own stream key — your YouTube key. It defaulted to `rtmp://a.rtmp.youtube.com/live2`, so the key
crossed the public internet between the server and Google in the clear. True since v1; not
introduced by v4, but v4 is the release that made key handling the point.

The default is now **`rtmps://a.rtmps.youtube.com/live2`**. YouTube accepts RTMPS on 443, ffmpeg
already speaks it, and the per-key destination validator already accepted `rtmps://` — so this is a
default change, not new machinery.

**Mind the hostname.** YouTube's RTMPS ingest is `a.rtmp`**`s`**`.youtube.com`, not
`a.rtmp.youtube.com`. Port 443 on the latter serves a certificate covering only `rtmps.youtube.com`
and `*.rtmps.youtube.com`, so the obvious "add an s to the scheme" URL fails hostname verification
and the relay never connects at all.

This release originally shipped with that wrong hostname, and it reached the live server. It was
caught minutes later by checking what the relay was actually doing rather than trusting that the
change worked — the relay was logging `[tls @ …] IO error: End of file`, which is what a rejected
certificate looks like from inside ffmpeg. Corrected in 4.0.2.

## An explicit environment variable now wins over the stored value

Changing `DEFAULT_RELAY_EDGE` on an existing deployment did nothing, silently.

`settings` is written to `db.json` on first run, and `load()` merged it as
`{ ...base.settings, ...parsed.settings }` — stored last, so stored won. Any later change to the
environment variable was read into `config` and then discarded. On the live server the first-run
value `rtmp://a.rtmp.youtube.com/live2` was frozen in, and setting the variable would have looked
like it had been applied while changing nothing.

Now an explicitly provided `DEFAULT_RELAY_EDGE` or `DEFAULT_KEY_QUOTA` overrides the stored value,
and says so:

```
[db] DEFAULT_RELAY_EDGE overrides the stored default:
     rtmp://a.rtmp.youtube.com/live2 -> rtmps://a.rtmps.youtube.com/live2
```

"Explicitly provided" means present and non-empty, so leaving it blank keeps the stored value and
the runtime-editable behaviour is unchanged.

## Upgrading

```bash
git checkout v4 && git pull
docker compose up -d --build
```

Existing deployments keep their stored destination unless you set the variable. To move to RTMPS on
a deployment that already has the plain-rtmp value stored, put it in `.env`:

```ini
DEFAULT_RELAY_EDGE=rtmps://a.rtmps.youtube.com/live2
```

Per-key destinations set in the dashboard are untouched either way — this only changes the fallback.

## Verified

- Seeded a `db.json` with the old `rtmp://a.rtmp.youtube.com/live2` stored, started with
  `DEFAULT_RELAY_EDGE=rtmps://…`: the override logged, and the effective and persisted value became
  the rtmps one.
- Left blank: stored value retained, no log line.
- TLS from the container to `a.rtmps.youtube.com:443` → authorized, cert `rtmps.youtube.com`;
  to `a.rtmp.youtube.com:443` → rejected, `not in the cert's altnames`. Hence the hostname above.
