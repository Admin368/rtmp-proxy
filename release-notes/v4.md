# v4 — The API key moves to the Server URL

Branch `v4` · based on `v3.2.1`

Streamers no longer visit the dashboard when their destination rotates its stream key. The API key
lives in OBS's **Server** field; the **Stream Key** field holds the destination's own key and is
theirs to change.

## What changes in OBS

**Settings → Stream → Service: Custom…**

| Field | Was (v1–v3) | Now |
| --- | --- | --- |
| Server | `rtmp://host:4001/live` | `rtmp://host:4001/live?key=<api-key>` |
| Stream Key | `<youtube-key>?key=<api-key>` | `<youtube-key>` |
| Use authentication | unchecked | unchecked |

Set the Server field once. When YouTube issues a new stream key, paste it into Stream Key and carry
on — nothing on the proxy needs to change.

**The v1–v3 form still works.** A key presented on the stream key is still accepted, so existing
encoder profiles keep streaming and can be migrated whenever convenient. When both are present, the
Server URL wins.

## Why not OBS's "Use authentication" checkbox

That was the original idea, and it turns out not to be a credential field at all. Measured against a
real client: connecting as `rtmp://user:pass@host/live/KEY` sends a connect packet containing only

```json
{"app":"live","type":"nonprivate","flashVer":"FMLE/3.0 (compatible; Lavf58.29.100)",
 "tcUrl":"rtmp://127.0.0.1:1999/live"}
```

— no username, no password anywhere. RTMP has no credential field in `connect`. What OBS's checkbox
drives is the **Adobe/Limelight `authmod` challenge-response**: librtmp's `PublisherAuth()` only
sends credentials *after* the server rejects the connect with
`[ AccessManager.Reject ] : [ authmod=adobe ]`, then negotiates over two further round trips of
salt, challenge and MD5 response.

Supporting it would mean implementing that state machine inside a library that offers no hook for it
(`reject()` destroys the socket rather than sending a challenge), and storing an MD5 verifier per
key instead of a one-way hash. Deferred deliberately.

The useful part: `PublisherAuth()` delivers its credentials by appending them to the **app** string —
the same channel this release uses. So if the checkbox is ever supported, it builds on this rather
than replacing it.

## RTMPS ingest

Plain RTMP sends the whole connect handshake in the clear, and the API key is now part of it. That
is not a new exposure — v3 sent the key in the `publish` command, equally unencrypted — but it is
worth closing, and node-media-server already supports a TLS listener that was never enabled.

```ini
RTMPS_PORT=4443
RTMPS_KEY=/etc/letsencrypt/live/example.com/privkey.pem
RTMPS_CERT=/etc/letsencrypt/live/example.com/fullchain.pem
```

Publish the port and mount the certificate (both are commented in `docker-compose.yml`). When it is
on, the dashboard shows the `rtmps://` URL first and labels it preferred. Certificates are read once
at startup, so a renewal needs a container restart.

Off by default. The certificate paths are checked at startup and a bad one is a loud warning, not a
silently missing listener.

## One honest trade-off

**OBS shows the Server field in plain text.** The Stream Key field is masked; the Server field is
not. Moving the key there makes it visible on screen, in screenshots of the Stream settings page, and
potentially in OBS logs. The wire exposure is unchanged from v3, and RTMPS closes that, but neither
helps the OBS UI. If that matters more than the convenience, the v1–v3 form still works and keeps
the key in the masked field.

## Keeping the key out of the logs

node-media-server logs the entire connect object, including `tcUrl`, and uses `app` to build every
stream path. Both would have carried the key. The `preConnect` handler now strips the query from
`app`, `tcUrl`, `swfUrl` and `pageUrl` before anything else sees them — whether or not a recognised
credential field was found, so a stray query can never reach a stream path or a log line.

Verified: after publishing with a valid key, an invalid key and no key at all, the key appears
nowhere in stdout or stderr.

## Upgrading from v3.2.1

```bash
git checkout v4
docker compose up -d --build
```

Nothing to migrate — no database change, and existing keys keep working in either form. Accounts,
keys and quotas are untouched.

To move a streamer over, rotate or re-read their key from the dashboard and give them the new Server
URL; the reveal banner now shows it ready to paste.

## Verified

Locally, against a real RTMP client and a test sink:

- **v4 form** — `app="live?key=<key>"`, stream key `YT-KEY-AAAA-BBBB`: accepted, relayed, sink
  received `/live/YT-KEY-AAAA-BBBB`. The stream name passes through to the destination untouched.
- **v1–v3 form** — key on the stream key: still accepted and relayed.
- **No key** → refused, `no API key supplied on the server URL or the stream key`.
- **Invalid key on the Server URL** → refused, `API key not recognised`.
- **Log scrubbing** — key absent from stdout and stderr across all of the above; the connect line
  for the rejected attempt logged `app=live tcUrl=rtmp://127.0.0.1:4001/live`.
- **RTMPS** — with a self-signed certificate, `Node Media Rtmps Server started on port: 4443`, a
  publish to `rtmps://127.0.0.1:4443/live?key=<key>` accepted with
  `tcUrl="rtmps://127.0.0.1:4443/live"` and relayed through to the sink at 49 kbps.
- Dashboard reveal banner and Connect card show the right URLs, preferring `rtmps://` when enabled.

**Not verified:** the Docker image build, and OBS itself — the client-side testing used ffmpeg,
which implements the same protocol. Worth a single real OBS check before rolling out to streamers.
